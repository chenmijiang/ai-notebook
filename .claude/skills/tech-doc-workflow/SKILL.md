把对话或研究材料收敛为一篇围绕单一核心问题的技术文档。默认读者是有相关开发经验的进阶开发者，默认目标是建立可用于实践与决策的心智模型；只有用户明确要求或确认其他体裁时，才切换为 quick start、操作指南或参考手册。

> **触发边界**：只有用户明确要求整理、沉淀、生成或改造文档时才使用。普通技术提问、追问和讨论继续按普通对话处理。

## 入口

| 入口         | 素材来源           | 典型说法                        |
| ------------ | ------------------ | ------------------------------- |
| 对话沉淀     | 当前对话或研究结果 | 「把刚才聊的整理成一篇文档」    |
| 改造存量文档 | `docs/` 下已有文档 | 「把这篇重构 / 审校 / 改成符合规范」 |

两条入口使用同一套主题、研究、审校和发布规则。改造存量文档时，先识别保留、合并、删除和新增的内容；不得未经确认改动其他文档。

## 执行流程

### 1. 建立主题契约并确认

先从需求和现有材料推导一份简短主题契约和初步骨架，在同一轮展示给用户确认：

- 目标读者和前置知识
- 文档模式：默认“心智模型与决策”，或用户确认的其他模式
- 一个可判定的核心问题
- 中心主张：读者应带走的判断
- 非目标：明确不覆盖的相邻问题
- 完成标准：读者看完后能理解什么机制、判断什么边界、做出什么决策
- 初步章节、每章要回答的问题和预期关键结论

一篇文档只回答一个核心问题，并形成“机制理解—边界判断—实践决策”的闭环。若材料包含多个可独立成立的核心问题，提出拆分或系列化方案。新建文档必须等待这一轮确认；明确的小范围局部修订可以沿用原契约，但要说明主题和骨架不变。

### 2. 定向研究和证据地图

只研究主题契约需要回答的内容，不因发现相邻知识而扩大范围。优先使用标准、官方文档、源码和可复现实验，维护内部证据表：

| 关键断言 | 来源 | 适用范围或限制 |
| -------- | ---- | -------------- |

对版本敏感、反直觉、可争议、性能、安全和关键选型结论必须建立来源对应关系。无法验证且影响中心主张的内容必须删除或暂停并询问用户；边缘信息可明确标为“未验证”。

### 3. 设计骨架并确认

研究后补充证据列，形成“章节—本章问题—关键结论—证据”的精简表。骨架不采用固定模板；章节顺序必须体现认知依赖、因果链或决策路径，每章承担不可替代的问题。

如果研究结果要求改变目标读者、核心问题、中心主张、非目标或新增/删除一级章节，暂停并重新展示修订后的主题契约和骨架，等待确认。章节内顺序、示例、小节合并和措辞调整由 agent 自行处理。

### 4. 按骨架起草

正文只实现已确认的论证路径，遵循 `tech-docs-guide`。关键结论至少解释因果机制、成立条件或边界、一个会影响实践的失败模式或权衡，并提供相应证据。示例、表格、图解、FAQ、总结和速查表只有在增加信息或帮助导航时才保留。

标题直接表达主题和核心问题，不强制使用“完全指南/使用指南”。新文件名简洁反映主题；系列文档沿用仓库已有的编号命名方式。

### 5. 双 reviewer 辩论

派 Reviewer A 和 Reviewer B，均使用独立新鲜上下文；起草 agent 不得兼任 reviewer。

1. Reviewer A 按四个维度提出带证据位置的问题：主题与骨架、机制与证据、重复与删减、语言与模板痕迹。深度问题必须指出缺少的机制、边界、失败模式/权衡或来源；语言问题必须指出具体翻译腔、套话、无信息过渡或模板组件。
2. Reviewer B 不先重复全量审校，而是逐条质疑 A 的问题，补充遗漏，并对每条问题形成共同处理结论：保留并说明理由、修改并给出验收条件，或删除。
3. 两位 reviewer 无需措辞一致，但问题单结论必须一致。涉及核心范围、主张、关键事实或一级章节的分歧，暂停并询问用户；非核心分歧按删减优先处理。

### 6. 修改和复审

主 agent 按共同问题单修改，不擅自扩大主题。修改后确认每条问题达到验收条件；阻塞问题未清零不得发布。必要时重复审校，但连续多轮无实质进展则暂停并返回问题单。

### 7. 语言编辑

内容审校通过后，才可调用 `humanizer-zh` 做语言层编辑，处理 AI 腔和翻译腔。允许重写句式、段落衔接和表达顺序，使中文自然，但不得改变章节骨架、技术事实、论证顺序、限定条件、来源含义或代码，不得补写未经验证的内容。编辑后由 Reviewer B 复核技术含义和限定条件未漂移；主 agent 对比最终 diff。

### 8. 发布校验

满足以下全部条件才发布：

1. 主题契约和骨架已确认，且正文没有超出非目标范围；
2. reviewer 问题单无遗留阻塞项，双 reviewer 对处理结论一致；
3. 关键技术事实已由证据地图支持，或明确标注未验证；
4. 结构、格式和示例符合 `tech-docs-guide`；
5. `index.md` 已含条目且 `check:home` 通过；
6. Prettier 干净；
7. 读者能沿着清晰路径回答核心问题并做出相应决策。

`index.md` 和格式化由 PostToolUse hook 产出，本步只核验结果，不重复执行命令。

## 用户介入条件

以下情况必须暂停并询问用户：需求或模式无法判断；主题契约中的核心决策存在歧义；关键来源冲突；影响中心主张的事实无法验证；研究或审校要求改变核心范围；两个 reviewer 对核心问题无法统一；连续多轮没有实质进展。

## 与其他自动化的分工

- **本 skill**：主题收敛、研究、正文质量、双 reviewer 审校和语言编辑边界。
- **`tech-docs-guide`**：文档写作规范的唯一事实源。
- **PostToolUse hook**：重建 `index.md` 和执行 Prettier。
- **pre-push `check:home`**：拦截未更新的 `index.md`。
- **CodeRabbit**：commit 后审查 diff 和结构。
