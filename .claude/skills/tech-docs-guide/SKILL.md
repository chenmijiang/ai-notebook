> 本文件是 `docs/` 技术文档的写作规范底座。它规定文档如何表达，不规定主题研究、用户确认、审校或发布流程；这些规则由 `tech-doc-workflow` 负责。

## 定位和读者

默认面向有相关开发经验的进阶开发者，帮助他们建立心智模型并做出实践决策。文档模式可以是：

- **心智模型与决策**：解释机制、边界和工程权衡。
- **快速入门**：帮助读者尽快完成一个明确任务。
- **操作指南**：围绕步骤、配置、验证和排错组织。
- **参考手册**：按需提供稳定、可查找的事实。

除非用户明确指定或确认，使用第一种模式。无论采用哪种模式，都先围绕一个核心问题裁剪内容。

## 主题和结构

- 标题直接表达主题和核心问题，不强制使用“完全指南”或“使用指南”。
- 用清晰的标题层级组织内容；数字编号只在有助于导航时使用，不为格式整齐强行编号。
- 起草前先确定中心主张、前置知识、非目标和读者完成标准；正文中的每章、每节都必须服务中心主张。
- 章节顺序体现认知依赖、因果链或决策路径。每章回答一个不同的问题，不能只按素材出现顺序排列。
- 一篇文档只形成一个完整闭环。能独立回答另一个核心问题的内容应删除、另写文档或拆为系列。
- 每个关键结论只完整解释一次。其他位置只做导航、引用或提供新的决策信息；删除不增加信息的复述。
- 开头不强制写概述，结尾不强制写总结，FAQ、速查表、表格、图解和多个场景也不强制。只有能降低理解成本、补足证据或帮助决策时才使用。
- 不使用目录和章节分隔线（`---`）。

## 内容深度

围绕中心主张的关键结论，至少说明：

1. **机制**：为什么会得到这个结果，必要时解释输入、处理和输出的关系；
2. **边界**：成立条件、版本范围、限制或不适用情况；
3. **失败模式或权衡**：错误时如何表现，或该选择牺牲了什么；
4. **证据**：标准、官方文档、源码或可复现实验中的依据。

非核心知识不为追求“完整”而展开。不要用更多术语、表格、代码或场景替代机制解释和边界分析。

## 语言

- 使用自然、准确的简体中文；技术术语保留行业惯用表达。
- 按中文技术写作习惯重组句子，不逐句对应英文语序。
- 优先使用明确主语、主动句和短句；把抽象名词还原为具体动作、条件和结果。
- 删除没有信息增量的过渡句、泛化价值判断、机械排比、空泛的“我们将……”和模板化结论。
- 避免翻译腔：过长定语、被动句堆叠、英语式名词化、直译连接词和不符合中文习惯的抽象表达。发现翻译腔时，改写句式和衔接，不改变技术含义。
- 避免 AI 腔：不为显得完整而堆叠固定组件，不反复使用同一种开场、总结或提示话术，不用宣传性语言替代具体判断。
- `✅/❌` 不是固定格式。只有需要并列表达可取与不可取做法时才使用，且必须说明原因。

## 示例和格式

- 代码块标注语言类型（如 `bash`、`json`、`javascript`）；需要 JSON 注释时使用 `jsonc`。
- 示例只包含理解或验证当前结论所需的代码。能运行时提供最小可运行示例，并说明运行条件和预期结果；无法运行的片段明确其边界。
- 代码注释只解释关键步骤、原因或限制，使用中文；不复述代码本身。
- 复杂关系或因果链可使用 ASCII 或 Mermaid 图，但图必须比文字更容易理解；否则删除。
- 表格只用于并列比较、字段速查或压缩重复信息，不能把连续论证拆成表格。
- 操作步骤按实际执行顺序编号，并包含必要的验证或失败处理。
- 关键事实在正文中使用 Markdown 链接就近指向来源，尤其是版本敏感、反直觉、可争议、性能、安全和选型结论；文末参考资源只列实际使用过的权威来源。

## 完成检查

交稿前逐项确认：

- 读者能用一句话说出文档回答的核心问题和中心主张；
- 每章都有不可替代的问题，并沿一条清晰路径推进；
- 关键结论具备机制、边界、失败模式或权衡及证据；
- 删除重复解释和没有信息增量的格式组件；
- 示例、命令和代码与正文结论一致；
- 中文表达自然，没有明显翻译腔、AI 腔或无意义的模板句。
